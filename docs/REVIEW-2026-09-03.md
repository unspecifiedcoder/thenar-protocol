## 1. What the plan intends to build (reconstructed)

- **Thesis.** THENAR is the neutral provenance and rights ledger for
  physical-AI training data — "Certificate Transparency for machine
  experience." Not capture, not hardware, not a marketplace, not a token.
- **Wedge.** The *Provenance Report*: ingest an existing LeRobot v3 corpus,
  commit every episode to a public append-only log, run checks, anchor,
  deliver a counsel-readable report with proofs and an on-chain licence
  receipt. Then a recorder SDK.
- **Product surfaces.** Ingest API, log service, verification workers,
  report, `/verify`, `LicenceRegistry` for terms/receipts/settlement,
  consent/revocation service.
- **Architecture.** Off-chain RFC 6962 log + sparse-Merkle revocation tree;
  heads anchored on a primary EVM chain (Avalanche C-Chain) and mirrored;
  four fixed-width leaf types; content-addressed file store; stateless
  on-chain verifier; one registry contract.
- **Trust model.** THENAR is trusted not to omit (mitigated by receipts,
  audit, mirrors, multisig); THENAR is verifier #1; suppliers are trusted
  only to the extent of their keys; the chain is trusted for ordering and
  timestamps; nothing trusts the payload.
- **Claim ladder.** L0 committed, L1 signed, L2 attested, L3 checked, L4
  reputed — each with fixed wording.
- **Cryptographic guarantees.** Inclusion, append-only consistency,
  consent non-membership, revocation onset, receipt binding
  `(buyer, termsHash, corpusRoot, corpusManifestHash, amount)`.
- **Physical-world limits.** Nothing proves a sensor reading was true.
  L2 proves which key signed, not which sensor produced bytes. L3 is
  heuristic.
- **Economics.** Report fees, SaaS/per-episode logging, 2.5% settlement
  take. No curator economics in v2.
- **Avalanche role.** Primary anchor + USDC settlement; protocol
  chain-agnostic; Ethereum/Sepolia mirror; L1 reserved for a consortium.
- **Golden demo.** Ingest → checks (one jittered duplicate fails) → anchor
  on two chains → seal corpus → licence in USDC → download + offline verify
  → revoke with onset → historical receipt still verifies → tamper detected.

## 3. Cryptography audit (result)

Every hash now cites an input rule:

| Object | Bytes hashed | Rule |
| --- | --- | --- |
| Log leaf | `0x00 ‖ preimage` | §10.1 |
| Log node | `0x01 ‖ l ‖ r` | §10.1 |
| SMT node | `l ‖ r`, `H(0,0)=0` | §10.2 |
| File leaf | `0x00 ‖ utf8(path) ‖ 0x1f ‖ keccak(fileBytes)` | §10.4 |
| payloadHash | CT root over sorted file leaves as level-0 nodes | §10.4 |
| manifestHash | `keccak(utf8(JCS(manifest − signature)))` with sorted arrays | §9.1, §10.5 |
| consentKey | `keccak(0x02 ‖ recordHash)` | §9.4 |
| consentCommitment | `keccak(recordHash ‖ salt32)` | §10.5 |
| revocation value | `keccak(recordHash ‖ utf8("revoked"))` | §10.2 |
| corpusRoot | CT root over episode leaf hashes as level-0 nodes | §10.7 |
| capTableHash | removed (no cap table in v2) | — |
| detailHash / claim message | `keccak(JCS(detail))`; sig over `domain‖0x00‖keccak(JCS(claim − signature))` | §10.6 |
| Signature message | `utf8(domain) ‖ 0x00 ‖ objectHash` | §10.6 |

Domain separation: leaf 0x00 / node 0x01 / consentKey 0x02 / four ASCII
signature domains. Replay: signatures bind to a specific object hash; append
receipts include `leafIndex` and `logSizeAfter`; revocations are idempotent
by construction. Versioning: leaf version byte; manifest `v`; check ids
append-only. Determinism: JCS + fixed-width leaves + bytewise sorts.

## 4. Log architecture (result)

Append-only, monotonic head (now: size non-decreasing with the revocation
exception), consistency, canonical ordering by log index, independent audit
via `/anchors/audit` and append receipts, mirror anchoring by `(root, size,
revocationRoot)`. **Corpus ≠ log**: a corpus is a separate tree over
selected episode leaf hashes, described by a manifest whose leaf is logged;
`sealCorpus` verifies that leaf's inclusion; buyers verify each episode's
inclusion in both trees. A corpus can never equal a log prefix by accident
because `corpusRoot` is over leaf hashes without the 0x00 prefix at level 0
— it is a different construction from the log root over the same leaves.

## 7. Hardware attestation (result)

Trusted: manufacturer roots pinned in repo; hardware-resident key; the
attested key equals the registered key; challenge nonce ties attestation to
a registration (not to each capture). Not solved: binding sensor bytes to
the key (impossible without a sensor-side signer); Quest attestation (unverified);
Jetson (no TPM by default). Firmware/OS versions recorded from attestation
extensions when present. Rotation: new key + new attestation; compromise:
`validTo` set; claims/manifests anchored before compromise remain valid,
after it invalid. Honest claim: *"signed by a key that cannot be extracted
from a device of model M."* L2 moved to Phase D.

## 8. Revocation and rights (result)

See PLAN §6.1 matrix. Summary: only the consent record's key holder can
revoke (contributor or, under W1, the supplier organisation); revocation is
an SMT entry with proven onset; the leaf stays; existing receipts stay
valid and auditable; new corpora cannot include the episode (off-chain
validation); access already delivered is not clawed back by the protocol;
rights after onset are governed by terms (FRONTIER wording).

## 9. Identity and keys (result)

Steward: Safe 2-of-3. Anchorer: relayer EOA that can only `anchor()`,
replaceable by the Safe. Verifier: Ed25519 in KMS, registered as an org key
with role `verifier`. Org keys: registered via API, append-only validity
windows. Contributor keys: SDK-generated Ed25519, per-episode consent
records. Buyer: EVM wallet. Rotation: append. Compromise: `validTo`;
validity evaluated at first-anchor time.

## 10. Data model (result)

Added `Dataset` and `Upload`; removed `Curator`, cap table; `Consent` is
per episode; every entity has an identifier, serialisation rule, version,
owner, lifecycle. No circular references.

## 18. MVP boundary

After v2.1, the wedge needs: Phase A (protocol), Phase B (SQLite log
service, uploads, ingest, proofs, daemon), Phase C (checks), report,
`/verify`, a licence script, the demo. It needs no hardware, no SDK, no
attestation, no marketplace page, no dashboard, no Postgres, no indexer, no
token, no L1. Those are Phase D/F, explicitly optional.

## 19. Golden demo — minimum

Ingest a public dataset → checks (one injected jittered duplicate fails) →
anchor primary + mirror → seal → licence via script with mock USDC →
download + offline verifier → revoke one episode → historical receipt
still verifies → tamper caught. SDK and attestation steps removed from the
minimum (available as extensions).
